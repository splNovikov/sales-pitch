# Roadmap: от MVP до полноценной платформы

Источник: `docs/TZ-general.md`

## Подход к roadmap

Ниже приведены 3 рабочих формата, в которых можно было бы оформить roadmap:

1. Короткая roadmap только по фазам.
Плюсы: быстро читается, удобно для презентации.
Минусы: плохо видны зависимости, сложно использовать как рабочий документ команды.

2. Roadmap по модулям продукта.
Плюсы: хорошо видно развитие отдельных подсистем.
Минусы: теряется бизнес-логика запуска, сложнее согласовывать приоритеты.

3. Phase-based roadmap с таблицами, scope, ограничениями и критериями готовности.
Плюсы: лучший баланс между стратегией и исполнением, удобно для стейкхолдеров, продакта и команды.
Минусы: документ длиннее, чем простая фазовая выжимка.

Рекомендуемый вариант: `3`. Он лучше всего подходит для данного ТЗ, потому что в продукте есть сильные зависимости между сущностями `ТС -> доступность -> прайсинг -> контракт -> бронь -> интеграции`.

## Продуктовая логика развития

Платформу стоит развивать не как "каталог ТС", а как систему подтверждаемого бронирования через агента:

1. Сначала доказать работоспособность операционного контура.
2. Затем сделать продукт коммерчески пригодным для регулярной работы нескольких компаний.
3. После этого расширить его до CRM и интеграционной платформы.
4. В финале превратить решение в экосистему с мультирегиональностью, мобильными приложениями и расширенной монетизацией.

## Принципы приоритизации

В каждую фазу попадает только то, что:

- напрямую влияет на основную ценность продукта;
- необходимо для следующей фазы;
- не создаст архитектурный тупик в будущем.

В MVP и ранних релизах сразу должны быть заложены архитектурные основы:

- единые сущности для всех ролей;
- role-based access;
- API-first подход;
- аудит и логирование;
- хранение времени в `UTC` с timezone;
- i18n-ready структура;
- мультивалютная модель данных;
- запрет двойного бронирования;
- расширяемая модель ТС и карточек.

## Этап 1. MVP / Pilot

### Цель

Подтвердить, что платформа решает главную проблему из ТЗ: позволяет собственнику и агенту работать в едином контуре без ручной синхронизации и без двойных броней.

### Бизнес-результат этапа

- 1-3 собственника и 1-2 агента работают в одной системе.
- Есть минимум один стабильный сценарий получения броней через агента.
- Бронь создается, подтверждается, отображается в календаре и не конфликтует с другими бронями.
- Данные по ТС, доступности и цене доступны через интерфейс и API.

### Scope MVP

| Блок | Что входит в MVP |
|---|---|
| Аутентификация и компания | Регистрация, вход по email/password, базовый профиль компании и пользователя |
| Ролевая модель | Собственник, агент, комбинированная роль на базе единой учетной записи |
| ТС | Создание и редактирование карточки ТС, фото, статус активности, общие и ключевые типовые характеристики |
| Модель данных ТС | Расширяемый тип ТС, шаблон карточки, обязательные и опциональные поля |
| Календарь | Доступно, в процессе бронирования, забронировано, недоступно; дневной и периодный сценарии |
| Прайсинг | Базовая цена, валюта, минимальный период, price override на дату или период |
| Контракты | Назначение агенту доступа к выбранным ТС, период действия контракта, базовые условия |
| Бронирование | Создание брони, проверка доступности, блокировка дат, статусы брони, отмена |
| Агентский контур | Просмотр доступных ТС, календаря, цен, ручное создание брони |
| API | Базовые endpoints для списка ТС, деталей ТС, availability, pricing, bookings |
| Уведомления | Email по новой брони, изменению статуса, напоминанию |
| Аудит | Логирование изменения броней, доступов и цен |

### MVP best practice

Лучший практический вариант для MVP:

- веб-платформа first;
- один регион;
- 2 языка: `RU` и `EN`;
- одна основная валюта per market, но модель данных сразу мультивалютная;
- ручной операционный процесс вокруг брони допускается;
- отсутствие встроенных платежей допустимо;
- весь фокус на надежности календаря, контрактов и бронирования.

### Что не включать в MVP

- нативные мобильные приложения;
- полноценную CRM;
- Telegram-реферальную программу как обязательную часть ядра;
- рейтинги, отзывы, форум;
- хранение документов и ЭДО;
- сложную аналитику;
- двустороннюю синхронизацию с внешними календарями;
- встроенную обработку платежей между участниками;
- community и marketplace исполнителей.

### Критерии готовности MVP

| Критерий | Целевое значение |
|---|---|
| Активные собственники | не менее 2 |
| ТС у активных собственников | не менее 3 у каждого пилотного собственника |
| Активные агенты | не менее 1 |
| Контракты | не менее 2 активных контрактов |
| Успешные брони | не менее 10 за первый месяц |
| Критические ошибки | 0 в первый месяц |
| Время ответа платформы | < 2 сек на ключевых сценариях |
| Двойные брони | 0 |

### Основные риски MVP

- недооценка сложности календаря и конфликтов бронирования;
- попытка преждевременно включить CRM и платежные сценарии;
- отсутствие нормальной модели доступов;
- ручные процессы вокруг подтверждения брони останутся вне системы и снизят ценность продукта.

## Этап 2. Release 1.0

### Цель

Сделать продукт не просто пилотным инструментом, а основной операционной системой для собственников и агентов.

### Ключевая идея этапа

На этом шаге продукт становится удобным для ежедневной работы, а не только для проверки гипотезы.

### Scope Release 1.0

| Блок | Что добавляется |
|---|---|
| Интерфейс | Единая навигация по задачам: `Собственный флот`, `Продажи`, `Аналитика`, `Настройки` |
| Флот | Явное разделение: собственные ТС, ТС в управлении, ТС по агентскому доступу |
| Календарь | Массовое редактирование, повторяющиеся правила, визуализация цены, фильтрация |
| Прайсинг | Сезонность, выходные/будни, праздничные цены, скидки на длительность |
| Виджет | Встраиваемый JavaScript-виджет для площадок агентов |
| Подписки | Базовые тарифы для собственников и агентов |
| Доступы | Пользователи компании, базовые роли сотрудников, настройки уведомлений |
| Аналитика | Загрузка ТС, брони по агентам, часы по ТС, базовые деньги и авансы |
| Бронирование | Политики отмены на уровне ТС, улучшенное управление статусами |
| Безопасность | API-ключи с уровнями доступа, усиление контроля доступа, базовые security policies |

### Что это дает бизнесу

- продукт можно продавать как основной инструмент управления парком и продажами;
- агент получает не только API, но и готовый виджет;
- собственник получает прозрачность по загрузке ТС и агентам;
- появляется базовый биллинговый контур платформы.

### Что еще не делаем

- полноценную CRM сделок и клиентской базы;
- глубокую автоматизацию маркетинга;
- мобильные приложения;
- рейтингование и social-layer;
- сложные marketplace-сценарии.

### Exit criteria Release 1.0

- пилотные клиенты регулярно работают в системе без возврата в таблицы;
- виджет и API используются на внешних площадках;
- подписочная модель начинает применяться;
- базовая аналитика влияет на операционные решения клиентов.

## Этап 3. Release 2.0

### Цель

Превратить продукт из системы бронирования и операционного учета в полноценную CRM-платформу для участников рынка.

### Scope Release 2.0

| Блок | Что добавляется |
|---|---|
| CRM | Сделки, работа менеджеров, коммуникации, внутренний процесс продаж |
| Клиенты | База клиентов, история бронирований, поиск, предпочтения, связанные сущности |
| Реферальная программа | Коды, скидки, отслеживание реферальных связей, интеграция с Telegram/API |
| Документы | Хранение связанных документов по ТС, пилотам, контрактам, бронированиям |
| Интеграции | Подключение внешних CRM, импорт данных, маппинг и валидация |
| Календари | Интеграция с Google Calendar / Outlook |
| Монетизация | Более зрелая тарификация, платные интеграции, store-подход |
| Аналитика | Отчеты по клиентам, менеджерам, каналам, движению денег |
| Клиентский контур | Архитектурная подготовка к клиентскому кабинету, частичная реализация API |

### Бизнес-результат этапа

- продукт удерживает не только собственников и агентов, но и внутренние команды продаж;
- появляется высокая switching cost;
- CRM становится аргументом для апсейла и роста ARPU;
- платформа начинает закрывать большую часть операционного контура клиента.

### Что переносится дальше

- community и форум;
- система рейтингов и репутации;
- расширенный marketplace исполнителей;
- полноформатные AI-функции как отдельный продуктовый слой.

### Exit criteria Release 2.0

- клиенты ведут не только бронь, но и значимую часть клиентской работы внутри платформы;
- импорт данных из внешних систем используется в реальных внедрениях;
- расширенная аналитика влияет на продажи и загрузку флота;
- интеграции становятся частью коммерческого предложения.

## Этап 4. Release 3.0

### Цель

Построить сетевой эффект и расширить продукт до отраслевой экосистемы.

### Scope Release 3.0

| Блок | Что добавляется |
|---|---|
| Discovery | Каталоги собственников, агентов, ТС, более развитый matching |
| Экосистема ролей | Добавление исполнителей: гиды, фотографы, музыканты, кейтеринг и др. |
| Репутация | Рейтинги, отзывы, оценки, история качества работы |
| Community | Форум, обмен опытом, отраслевые механики взаимодействия |
| Mobile | Нативные приложения `iOS` и `Android` |
| Advanced analytics | Прогнозирование спроса, расширенные отчеты, performance dashboards |
| Monetization expansion | Дополнительные платные модули, premium features, новые модели тарификации |

### Бизнес-результат этапа

- платформа становится не только операционной системой, но и точкой притяжения рынка;
- усиливается эффект "чем больше участников, тем выше ценность";
- появляются новые каналы монетизации и удержания.

### Ограничения этапа

Этот этап следует запускать только после того, как:

- подтвержден PMF на ядре продукта;
- внедрения идут повторяемо;
- есть стабильная экономика пилотов и первых коммерческих клиентов;
- операционная часть и CRM работают устойчиво.

## Этап 5. Full Solution / Scale

### Цель

Довести продукт до полноценного решения, описанного в ТЗ: масштабируемой мультирегиональной платформы с сильной архитектурой, зрелой монетизацией и возможностью выхода в новые рынки.

### Scope Full Solution

| Направление | Что должно быть реализовано |
|---|---|
| География | Мультирегиональное развертывание, локализация данных, routing по регионам |
| Языки | Полноценная мультиязычность beyond RU/EN |
| Валюты | Мультивалютность, правила отображения и конвертации |
| Часовые пояса | Корректная timezone-модель на всех пользовательских и интеграционных сценариях |
| Масштабирование | Stateless backend, read replicas, cache layers, очереди, CDN, autoscaling |
| Наблюдаемость | Метрики, алерты, error tracking, performance monitoring, аудит |
| Надежность | Backup/restore, DR-план, зрелый CI/CD, эксплуатационные регламенты |
| Безопасность | Шифрование чувствительных данных, 2FA, строгие политики доступа, compliance-ready процессы |
| API platform | Версионирование API, webhook ecosystem, внешние интеграционные сценарии |
| Биллинг | Учет тарифов, подписок, платных модулей и интеграций |
| PWA / Mobile continuity | Бесшовная работа между web, mobile web, PWA и native apps |

### Финальное целевое состояние

Полноценное решение из ТЗ в зрелом виде выглядит так:

- единая платформа для собственников, агентов и в перспективе исполнителей;
- единая модель данных по ТС, бронированиям, контрактам, клиентам и интеграциям;
- полноценный web-продукт плюс mobile layer;
- CRM, discovery, аналитика, подписки и интеграции в одном контуре;
- архитектура, позволяющая расширяться по рынкам, ролям и бизнес-моделям.

## Что нужно заложить с первого дня, даже если фича появится позже

### Обязательно закладывать в архитектуру сразу

- мультиязычность;
- мультивалютность;
- timezone-aware даты и время;
- единые сущности для owner/agent/client;
- расширяемую карточку ТС;
- историю изменений и аудит;
- гибкую модель доступов;
- API-ключи и интеграционный слой;
- модель подписок и feature flags;
- готовность к CRM и клиентскому кабинету.

### Почему это best practice

Если не заложить это в MVP, позже придется делать дорогой рефакторинг:

- пересобирать модель данных;
- ломать API;
- менять логику прав доступа;
- переписывать календарь и прайсинг;
- усложнять выход на новые регионы.

## Рекомендуемая последовательность delivery

1. `MVP / Pilot`
Проверка продуктового ядра на реальных бронированиях.

2. `Release 1.0`
Доведение операционного контура до коммерчески пригодного уровня.

3. `Release 2.0`
Подключение CRM и интеграций как драйверов удержания и роста.

4. `Release 3.0`
Формирование сетевого эффекта и рыночной экосистемы.

5. `Full Solution / Scale`
Международный масштаб, зрелая архитектура и расширенная монетизация.

## Рекомендация по управлению roadmap

Для работы со стейкхолдерами roadmap лучше вести в трех уровнях:

1. `Strategic roadmap`
Фазы `MVP -> 1.0 -> 2.0 -> 3.0 -> Full Solution`.

2. `Quarter roadmap`
Крупные блоки delivery внутри фазы.

3. `Execution backlog`
Эпики, фичи, user stories, acceptance criteria.

Это лучший практический подход, потому что он не смешивает стратегию продукта с проектным бэклогом команды.

## Краткий executive summary

Продукт нужно запускать как веб-платформу для подтверждаемого бронирования через агента, а не как "еще одну CRM" или "просто каталог ТС". MVP должен доказать надежность ядра: карточка ТС, календарь, прайсинг, контракты, бронь, API и уведомления. Версия `1.0` делает систему операционно пригодной и монетизируемой. Версия `2.0` превращает ее в CRM-платформу. Версия `3.0` формирует экосистему и сетевой эффект. Финальная стадия выводит продукт на мультирегиональный и масштабируемый уровень, полностью соответствующий целям ТЗ.
