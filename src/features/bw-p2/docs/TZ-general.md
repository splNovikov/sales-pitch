## 1. Определение проблемы и цели

### 1.1 Утверждение

В настоящее время рынок аренды транспортных средств (лодок, катеров, автомобилей, гидроциклов, квадроскутеров, вертолётов, самолётов и т.д.) **не имеет единого инструмента** для агентов, которые выступают связующим звеном между:
- **Владельцами/собственниками** парков транспортных средств
- **Клиентами**, желающими арендовать ТС

Агенты вынуждены использовать:

#### 1.1.1 Разрозненные инструменты
- Электронные таблицы, старые системы брони

#### 1.1.2 Ручное управление
- Ручное управление доступностью и стоимостью
- Несинхронизированные данные между разными площадками
 - Регулярные ручные запросы доступности и подтверждения бронирования через чат/звонок и дублирование информации по каждой брони для трёх сторон (агент, клиент, судовладелец)

### 1.2 Целевое состояние

#### 1.2.1 По возможностям платформы

Создать **универсальную платформу**, которая позволит:
- Собственникам публиковать информацию о ТС и управлять доступностью
- Агентам получать доступ к информации о ТС и системе бронирования через контракты с собственниками (доступ, предоставляемый платформой), интегрировать данные на собственные площадки через виджеты/API, управлять бронями и отслеживать статистику
 - Клиентам бронировать ТС через онлайн площадки собственников и агентов, с возможностью отслеживать историю заказов, видеть подписанные документы и договоры, получать своевременный и качественный сервис от исполнителей
- Всем участникам отслеживать бронь в едином календаре
 - Вести расчёт заработной платы капитана, смен, топлива и других операционных издержек, а также отслеживание лодки (через собственный инструмент платформы или интеграцию с уже используемыми внешними системами)
 - Интегрировать онлайн-кассу для работы с фискальными чеками и легального оформления платежей (на старте — базовая интеграция, детали см. в разделах про оплату и документы)

**Важно:** Собственник может выступать в роли агента для своих собственных ТС, используя комбинированный интерфейс.

**Главная особенность и конкурентное преимущество платформы**

- Платформа обеспечивает **взаимодействие между клиентом и собственником через агентов** — это её основное отличие.
- Агент берёт на себя **ответственность по подтверждению брони с собственником**. Платформа поддерживает **бронирование с ожиданием подтверждения** (аналог бронирования мест в кинозале): клиент бронирует ТС на площадке, выбирая свободное время/окно и утверждая его; после этого ему даётся время на внесение предоплаты/оплаты для подтверждения брони. После подтверждения клиенту высылается информация о прогулке.
- Благодаря такой схеме **исключается недопонимание**, когда клиент через систему что-то забронировал «напрямую», собственник этого не увидел, а клиент приехал на дату встречи — и никого нет. Взаимодействие через агента, который подтверждает доступность ТС у собственника, гарантирует, что бронь согласована со всеми сторонами.

**Ключевая связка платформы:** бронирование с подтверждением посредством агентов.

#### 1.2.2 По регионам и языкам

- Поддержка множества регионов и языков с возможностью масштабирования.
- **Языки MVP:** русский и английский.
- **Валюты:** поддержка нескольких валют с ориентацией на быстрый выход через Дубай; архитектура должна предусматривать хранение цен в нескольких валютах и при необходимости конвертер.

#### 1.2.3 По платформам и продукту

- Нативные мобильные приложения для iOS и Android
- Веб-платформа остаётся доступной для всех пользователей
- Единая backend-архитектура для всех платформ
- В финальной версии продукт должен представлять собой законченную и полноценную CRM

Первая итерация (MVP) см. раздел 11.2.

### 1.3 Мультирегиональность и мультиязычность

- **Мультирегиональность:** Платформа должна поддерживать работу в различных регионах (Россия, Дубай, и другие регионы)
- **Мультиязычность:** Интерфейс и контент должны поддерживать несколько языков; на старт (MVP) — русский и английский
- **Валюты:** поддержка нескольких валют с учётом быстрого захода через Дубай; архитектура данных должна предусматривать мультивалютность
- **Часовые пояса:** система должна хранить даты/время в нормализованном виде (UTC) с привязкой к часовому поясу ресурса и пользователя; корректное отображение времени в интерфейсе для разных ролей и регионов
- **MVP-старт:** Сфокусирован на 1-3 собственниках и 1-2 агентах в одном регионе

Целевое состояние по регионам и языкам см. п. 1.2.2.

## 2. Анализ конкурентов

### 2.1 YClients

#### 2.1.1 Чем не подошёл

- Система не покрывает потребности компании: отсутствует бронирование с подтверждением и взаимодействие между агентами и владельцами.
- Не подходит для сценариев BW с агентами и партнёрами.

### 2.2 Конкурентные преимущества нашего продукта

- **Главное отличие:** Взаимодействие «клиент — собственник» через агентов и модель **бронирование с подтверждением агентом**; агент подтверждает доступность у собственника, что исключает ситуацию «клиент забронировал, собственник не видел, клиент приехал — никого нет».
- **Ключевое отличие:** Исключение человеческого фактора и единая система для управления различными видами услуг: трансферы, спецтехника, аренда катеров.
- **Актуальность рынка:** Автоматизация востребована в разных странах, в т.ч. в сфере яхтинга.

## 3. Ролевая модель

### 3.1 Принцип разделения ролей

- Разделение ролей определяется объёмом характеристик и элементов управления в интерфейсе, а не двумя разными видами учёток.
- Функционал для агентов и собственников различается — от этого зависит широта доступа и контроля.

### 3.2 Основные роли

#### **Собственник**
- Тот кто полностью распоряжается ТС. 100% прав пользования и распоряжения
- Владелец одного или нескольких транспортных средств (парка)
- Отвечает за предоставление информации о ТС
- Управляет доступностью и ценообразованием
- Получает информацию о бронях и авансах
- Имеет доступ к полному набору параметров и отчётов по своим ТС
- Может выступать в роли агента для своих собственных ТС

#### **Агент**
- Промежуточный участник, получающий доступ к ТС через контракты с собственниками (доступ к системе бронирования в платформе)
- Размещает информацию о ТС на собственных площадках/платформах
- Получает комиссию от каждой бронирования
- Управляет взаимодействием между клиентом и собственником
- Имеет доступ к параметрам и отчётам по своим клиентам и броням в полном объёме, а собственник получает только базово необходимую информацию для выполнения заказа
- Имеет возможность ручной формы бронирования через личный кабинет
- **Важно:** Собственник может одновременно выступать в роли агента

#### **Клиент**
- Конечный пользователь, желающий арендовать ТС
- Бронирует ТС через площадку агента
- Платит агенту, либо смежно: предоплату агенту, остаток в конце прогулки нал/безнал собственнику

## 4. Бизнес-требования: Транспортные средства

### 4.1 Типы транспортных средств

Платформа должна поддерживать различные типы транспортных средств:
- **Водный транспорт:** лодки, катера, яхты, гидроциклы, теплоходы
- **Наземный транспорт:** автомобили, квадроскутеры, мотоциклы
- **Воздушный транспорт:** вертолёты, самолёты, дроны
- **Специализированный транспорт:** снегоходы, багги и другие

**Требования:**
- [ ] Система должна быть расширяемой для добавления новых типов ТС
- [ ] Общие характеристики образуют базовую структуру карточки ТС; каждый тип ТС дополнительно имеет уникальный набор характеристик
- [ ] Возможность группировки ТС по категориям для удобной навигации

### 4.2 Характеристики и карточка ТС

Карточка ТС по сути есть набор характеристик (общие + специфичные для типа), представленный в интерфейсе в виде шаблона с полями.

#### 4.2.1 Общие характеристики (для всех типов ТС)
- Название/модель
- Марка/производитель
- Год выпуска
- Описание
- Фотографии (галерея) (и/или ссылка на материал)
- Видео (опционально)
- Статус (активно/неактивно)
- Закрытая/открытая цена, или % вознагрождения
- **Требования к пилоту/оператору:**
  - Потенциально у ТС может не быть пилота (хотя в 99% случаев пилот требуется)
  - Если пилот требуется, он может быть:
    - Пилот-собственник ТС (сам владелец управляет ТС)
    - Нанятый пилот (приглашённый специалист)
- [ ] **Хранение документов:** возможность хранения сканов лицензий пилотов, полисов страховки и других необходимых документов; полная реализация — к версии 2.0 (совместно с CRM и документооборотом)

#### 4.2.2 Специфические характеристики по типам ТС

**Водный транспорт (лодки, катера, яхты):**
- Тип судна
- Длина, ширина
- Вместимость (количество пассажиров)
- Тип двигателя (мотор, парус, гибрид)
- Мощность двигателя
- Максимальная скорость
- Водоизмещение
- Наличие кают, спальных мест
- Дополнительное оборудование (кондиционер, кухня, туалет)

**Воздушный транспорт (вертолёты, самолёты):**
- Тип воздушного судна
- Максимальная грузоподъёмность
- Вместимость пассажиров
- Дальность полёта
- Максимальная скорость
- Высота полёта
- Тип двигателя
- Наличие специального оборудования

**Наземный транспорт (автомобили, квадроскутеры):**
- Тип кузова
- Количество мест
- Объём двигателя
- Тип топлива
- Привод (передний, задний, полный)
- Коробка передач
- Дополнительные опции

**Примечание:** Список характеристик должен быть расширяемым для каждого типа ТС.

#### 4.2.3 Карточка ТС: шаблоны и требования

Карточка — представление того же набора характеристик в интерфейсе; для каждого типа ТС задаётся шаблон с полями.

- [ ] **Гибкая структура данных:** Система должна поддерживать различные наборы полей для разных типов ТС
- [ ] **Шаблоны карточек:** Предопределённые шаблоны для каждого типа ТС с обязательными и опциональными полями; шаблоны по типам ТС сокращают ручной ввод и унифицируют данные
- [ ] **Расширяемость:** Возможность добавления кастомных полей для специфических случаев
- [ ] **Валидация:** Проверка корректности заполнения полей в зависимости от типа ТС
- [ ] **Отображение:** Адаптивное отображение карточки в зависимости от типа ТС (разные блоки информации, приоритеты полей)

#### 4.2.4 Примеры группировки полей в карточке

**Карточка лодки:**
- Основная информация (название, тип, год)
- Технические характеристики (длина, ширина, вместимость, двигатель)
- Комфорт и оборудование (каюты, кухня, кондиционер)
- Фотографии и видео
- Лицензионные требования

**Карточка вертолёта:**
- Основная информация (модель, тип, год)
- Лётные характеристики (грузоподъёмность, дальность, скорость)
- Вместимость и комфорт
- Фотографии и видео
- Требования к пилоту и документам:
  - Наличие пилота (обязательно/не требуется)
  - Тип пилота (пилот-собственник / нанятый пилот)
  - Требуемые лицензии и документы

## 5. Бизнес-требования: Прайсинг транспортных средств

### 5.1 Модель ценообразования

#### 5.1.1 Базовая цена
- [ ] Базовая цена за единицу времени (час, день, смена)
- [ ] Выбор единицы измерения цены (зависит от типа ТС)
- [ ] Валюта цены (RUB, USD, EUR, AED и т.д.)
- [ ] Минимальный период аренды

#### 5.1.2 Динамическое ценообразование
- [ ] **Сезонное ценообразование:**
  - Высокий сезон (повышенные цены)
  - Низкий сезон (пониженные цены)
  - Промежуточные периоды
- [ ] **Дневное ценообразование:**
  - Разные цены в будние дни и выходные
  - Специальные цены в праздничные дни
- [ ] **Временное ценообразование:**
  - Цены могут меняться в зависимости от времени суток (для некоторых типов ТС)
- [ ] **Скидки за длительность:**
  - Скидка за аренду на несколько дней/недель
  - Прогрессивные скидки (чем дольше, тем больше скидка)

#### 5.1.3 Дополнительные услуги и опции
- [ ] Ценообразование на дополнительные услуги:
  - Услуги пилота/оператора
  - Топливо
  - Страховка
  - Дополнительное оборудование
  - Трансфер к месту аренды
- [ ] Возможность комбинирования услуг в пакеты

### 5.2 Правила применения цен

- [ ] **Приоритет цен:** Система должна определять, какая цена применяется при конфликте правил (например, выходной день в высоком сезоне)
- [ ] **Расчёт итоговой стоимости:** Автоматический расчёт стоимости аренды с учётом всех правил и скидок
- [ ] **Прозрачность:** Клиент должен видеть детализацию цены (базовая цена, наценки, скидки)
- [ ] **История изменений цен:** Логирование всех изменений цен для аудита

### 5.3 Интеграция прайсинга с календарём

- [ ] Цены привязаны к конкретным датам в календаре
- [ ] При изменении доступности автоматически применяются соответствующие правила ценообразования
- [ ] Возможность установить специальную цену для конкретной даты или периода

## 6. Бизнес-требования: Календарь доступности и связка с прайсингом

### 6.1 Календарь доступности транспортных средств

#### 6.1.1 Статусы доступности
- [ ] **Доступно:** ТС свободно и может быть забронировано
- [ ] **В процессе бронирования:** заявка на бронь создана, ожидается подтверждение
- [ ] **Забронировано:** ТС уже забронировано на этот период
- [ ] **Недоступно:** ТС временно недоступно (техническое обслуживание, ремонт, личное использование)
- [ ] **Ограниченная доступность:** ТС доступно, но с ограничениями

#### 6.1.2 Типы периодов доступности

**Одноразовые события:**
- [ ] Конкретная дата или период (с-по)
- [ ] Установка статуса для конкретного дня/периода
- [ ] Блокировка на определённое время

**Повторяющиеся события:**
- [ ] Еженедельные паттерны (например, каждый понедельник недоступно)
- [ ] Ежемесячные паттерны (например, первое число каждого месяца)
- [ ] Сезонные паттерны (например, весь летний сезон)
- [ ] Кастомные повторяющиеся правила (каждые N дней, в определённые дни недели)

#### 6.1.3 Управление календарём
- [ ] Визуальный календарный интерфейс (месяц, неделя, день)
- [ ] Массовое редактирование периодов
- [ ] Копирование расписания между ТС (для парков)
- [ ] Импорт/экспорт календаря (опционально для MVP)

### 6.2 Связка календаря с прайсингом

#### 6.2.1 Динамическое ценообразование по календарю

**Связь дат и цен:**
- [ ] Каждая дата в календаре может иметь свою цену
- [ ] Правила ценообразования применяются автоматически на основе даты
- [ ] Приоритет правил: конкретная дата > выходной/будний день > сезон > базовая цена

**Примеры связки:**
- [ ] **Выходные дни:** Автоматическое применение повышенной цены в субботу и воскресенье
- [ ] **Праздничные дни:** Специальные цены в государственные праздники
- [ ] **Сезонность:** Автоматическое переключение между высоким и низким сезоном
- [ ] **Конкретные даты:** Установка специальной цены для конкретной даты (например, день рождения, корпоративное событие)

#### 6.2.2 Визуализация цены в календаре
- [ ] Отображение цены для каждой доступной даты
- [ ] Цветовое кодирование цен (например, зелёный - низкая цена, красный - высокая)
- [ ] Подсказки с детализацией цены при наведении
- [ ] Фильтрация по ценовому диапазону

#### 6.2.3 Автоматическое обновление цен
- [ ] При изменении календаря (добавление/удаление периодов) автоматически пересчитываются доступные цены
- [ ] При изменении правил прайсинга обновляются цены во всём календаре
- [ ] Уведомления о конфликтах правил (например, если установлена специальная цена на дату, которая попадает под выходной день)

### 6.3 Бронирование и календарь

- [ ] **Запрет двойного бронирования:** Система не позволяет забронировать уже занятую дату
- [ ] **Блокировка при бронировании:** При создании брони соответствующие даты автоматически блокируются в календаре
- [ ] **Освобождение при отмене:** При отмене брони даты автоматически становятся доступными
- [ ] **Частичное бронирование:** Возможность забронировать часть дня (для некоторых типов ТС)

## 7. Бизнес-требования: Бронирование транспортных средств

### 7.1 Процесс бронирования

Модель бронирования в платформе строится вокруг **подтверждения брони агентом у собственника** (бронирование с ожиданием подтверждения); это основа сценария «бронь в 2 клика» и исключения недопонимания между клиентом и собственником.

#### 7.1.1 Создание бронирования
- [ ] **Целевой сценарий «бронь в 2 клика»:** клиент может забронировать услугу без звонка
- [ ] Автоматизация подтверждения брони (сокращение времени и ошибок)
- [ ] Клиент выбирает ТС и даты на площадке агента (через виджет или API)
- [ ] Система проверяет доступность выбранных дат в реальном времени
- [ ] Отображение итоговой стоимости с детализацией (базовая цена, наценки, скидки)
- [ ] Заполнение данных клиента (имя, контакты, дополнительные требования)
- [ ] Подтверждение бронирования
- [ ] Автоматическая блокировка дат в календаре собственника

#### 7.1.2 Управление бронированием
- [ ] Просмотр статуса бронирования
- [ ] Изменение дат бронирования (при наличии доступности)
- [ ] Отмена бронирования (с учётом политики отмены, заданной для каждого ТС)
- [ ] Добавление примечаний и дополнительной информации
- [ ] Уведомления о статусе бронирования (email, в перспективе SMS/push)

### 7.2 Интеграция с CRM-системами

#### 7.2.1 Концепция интеграции
- [ ] На первых этапах — базовое приложение, интегрируемое с различными CRM
- [ ] Клиенты, уже использующие определённые CRM, подключают продукт без больших затрат на настройку
- [ ] Варианты: интеграция с внешними CRM или с собственной CRM заказчика
- [ ] Создание собственной CRM затратно; приоритет — интеграция с существующими системами
- [ ] Платформа должна быть способна интегрироваться с другими CRM-системами или с CRM заказчика; интеграция критична для полноценной работы продукта

#### 7.2.2 Процесс интеграции
- [ ] Импорт данных из существующих CRM (один из вариантов наряду с API и виджетами):
  - Список клиентов
  - История бронирований
  - Контакты и предпочтения клиентов
  - Исторические данные и статистика
- [ ] Маппинг данных между старой и новой системой
- [ ] Валидация импортированных данных
- [ ] Постепенный переход с возможностью параллельной работы (опционально)

#### 7.2.3 Преимущества и расширения
- [ ] Единый интерфейс для всех агентов
- [ ] Синхронизация данных в реальном времени
- [ ] Доступ к расширенной функциональности (календарь, прайсинг, аналитика)
- [ ] Интеграция с виджетами и API для собственных площадок
- [ ] Возможность интеграции с мессенджерами и сторонними сервисами для универсальности внутренней работы

### 7.3 Реферальная программа и монетизация

#### 7.3.1 Концепция реферальной программы
- [ ] **Цель:** Привлечение новых клиентов через существующих
- [ ] Клиенты получают скидки за привлечение друзей
- [ ] Отслеживание реферальных связей и начисление бонусов

#### 7.3.2 Первая итерация реферальной программы
- [ ] **Реализация через Telegram:**
  - Telegram-бот для регистрации реферальных кодов
  - Telegram-каналы для распространения реферальных ссылок
  - Интеграция с платформой через API
- [ ] Генерация уникальных реферальных кодов для клиентов
- [ ] Отслеживание использования реферальных кодов
- [ ] Начисление скидок при успешном привлечении новых клиентов

#### 7.3.3 Личный кабинет клиента (не в MVP, но предусмотреть)

**Статус:** Не входит в первую итерацию (MVP), но архитектура должна предусматривать возможность добавления в будущем.

**Планируемый функционал:**
- [ ] **История бронирований:**
  - Список всех прошлых и активных бронирований
  - Детали каждой брони (ТС, даты, стоимость, статус)
  - История изменений статусов
  - Возможность повторного бронирования
- [ ] **Реферальная программа:**
  - Личный реферальный код
  - Статистика привлечённых друзей
  - Начисленные реферальные скидки
  - История использования скидок
  - Реферальные ссылки для распространения
- [ ] **Управление платежами:**
  - Сохранённые карты оплаты
  - История платежей
  - Способы оплаты
  - Настройки автоплатежей (опционально)
- [ ] **Профиль и настройки:**
  - Личные данные
  - Контактная информация
  - Предпочтения (типы ТС, локации)
  - Настройки уведомлений
- [ ] **Бонусы и скидки:**
  - Доступные скидки и промокоды
  - Накопленные бонусы
  - История использования бонусов

#### 7.3.4 Технические требования для будущего ЛК
- [ ] Архитектура должна поддерживать добавление роли "Клиент" с расширенными правами
- [ ] API для интеграции с Telegram-ботом и другими каналами
- [ ] Система реферальных кодов и отслеживания связей
- [ ] Интеграция с платежными системами для сохранения карт
- [ ] Система бонусов и скидок

#### 7.1.3 Политика отмены броней
- [ ] Политика отмены задаётся **на уровне каждого ТС индивидуально**; у каждого собственника/ТС может быть своя.
- [ ] Пример шкалы штрафов: отмена за 7 дней — 30% штраф; за 3 дня — 70%; в день прогулки — до 100% штрафа.
- [ ] Альтернативные варианты: перенос прогулки без штрафа, бесплатная отмена за N суток до даты и т.п. — настраивается в карточке ТС.

#### 7.1.4 Сбор депозита перед арендой
- [ ] Возможность сбора депозита перед арендой — опционально; формат и логика требуют дополнительного обсуждения, но архитектура должна быть к этому готова.

### 7.4 Интеграция бронирования с агентскими площадками

- [ ] Бронирование через виджеты на сайтах агентов
- [ ] Заявки с виджетов, размещённых агентами на своих сайтах, автоматически попадают в CRM агента
- [ ] Бронирование через API интеграцию
- [ ] Синхронизация бронирований в реальном времени
- [ ] Единая система управления бронями для всех агентов
- [ ] Автоматические уведомления всем участникам процесса

### 7.5 Оплата, онлайн-кассы и документы

#### 7.5.1 Сценарии платежей между участниками
Платформа не обрабатывает платежи между клиентами, агентами и собственниками; ответственность за взаиморасчёты несут участники. Поддерживаемые сценарии:
- [ ] **Базовый сценарий:** клиент вносит предоплату в размере комиссии агента для подтверждения брони; остаток оплачивает собственнику (наличными или на реквизиты) в конце прогулки.
- [ ] **Альтернативный сценарий:** клиент полностью оплачивает агенту; агент рассчитывается с собственником по договорённости вне платформы.

#### 7.5.2 Онлайн-кассы и эквайринг
- [ ] Интеграция с онлайн-кассой — настраивается через банк или платёжный провайдер; приоритетные системы: онлайн-касса от банка, ЮKassa, Robokassa, Яндекс.Касса, КриптоКлауд.
- [ ] Комиссия эквайринга может увеличивать стоимость услуги — это не входит в зону ответственности BW.

#### 7.5.3 Выставление счёта юридическим лицам
- [ ] Стандартная форма, в которой клиент вводит свои реквизиты

#### 7.5.4 Договор об услугах
- [ ] При оплате клиент обязан подписать договор об услугах — это упрощает юридическое сопровождение

#### 7.5.5 Цель в контексте рынка
- [ ] Упрощение работы в «белой» системе и отход от наличных платежей; актуально в текущих условиях рынка

## 8. Монетизация платформы

### 8.1 Базовая модель монетизации (подписочная)

#### 8.1.1 Подписка для разных типов пользователей
- [ ] **Подписочная модель:** Платформа взимает плату за пользование системой, а не процент от оборота/продаж. Процентная модель монетизации не используется на старте — она жёсткая и редко привлекает участников. Оплачивают **все участники** (собственники, агенты, при расширенных тарифах — дополнительные исполнители) в зависимости от формы функционала и выбранного тарифа.
- [ ] **Подключение пользователей:** плата за подключение внутренних пользователей и регистраций (базово 1 пользователь + 1 за каждую новую учётку менеджера).
- [ ] **Отдельные тарифы для ролей** (или сразу расширенный тариф):
  - **Собственники:** своя линейка тарифов за использование платформы для управления ТС и флотом, с учётом количества единиц флота (например, 3 / 5 / 10 ТС и т.п.).
  - **Агенты:** своя линейка тарифов за доступ к функционалу продаж и интеграционным инструментам.
  - **Дополнительные исполнители:** гиды, фотографы, ведущие, музыканты и другие смежные роли.
  - **Кейтеринги** и прочие сервисные подрядчики.
  - **Добавление нового города/страны** с возможностью дифференцировать стоимость по регионам/странам.
- [ ] **Модель оплаты:** подписка или фиксированная плата за период (месяц/год), с возможностью изменения тарифной сетки в будущем.
  - Интеграции и настройки продукта.
  - Подключение **Store** для CRM и сторонних продуктов и месячная плата за пользование (например, подключение 3 аккаунтов Telegram менеджеров, каждый по 2000 ₽/месяц, подключение телефонии или AI-ассистента).
  - Внутренний **AI-помощник** платформы (ассистент в чатах, аналитике, показателях продаж и т.д.).
  - Настройка и создание сайтов и мобильных приложений с нашим функционалом (дочерний сервис по интеграции).

#### 8.1.2 Апгрейд ролей (пример: агент → собственник)
- [ ] Пользователь может начать как **агент** и позже расширить свои права до **собственника**.
- [ ] При переходе из статуса «только агент» в статус «агент + собственник»:
  - Пользователь **«докупает учётку»** — оплачивает дополнительный функционал собственника.
  - Применяется комбинированный тариф, учитывающий оба набора прав (агента и собственника).
- [ ] Модель должна поддерживать гибкое изменение набора функций и тарифа без создания отдельных аккаунтов.

#### 8.1.3 Что включает подписка
**Для собственников:**
- [ ] Управление ТС (создание, редактирование, удаление).
- [ ] Управление доступностью и календарём.
- [ ] Управление ценообразованием.
- [ ] Просмотр и управление бронями.
- [ ] Управление контрактами с агентами и пилотами.
- [ ] Базовые отчёты и статистика.

**Для агентов:**
- [ ] Доступ к информации о ТС через контракты.
- [ ] API-доступ для интеграции на собственные площадки.
- [ ] Виджеты для встраивания.
- [ ] Управление бронями.
- [ ] Просмотр контрактов и доступных ТС.
- [ ] Базовые отчёты и статистика.

#### 8.1.4 Важные ограничения
- [ ] **Платформа НЕ взимает процент от продаж** (на текущем этапе).
- [ ] Платформа НЕ обрабатывает платежи между клиентами, агентами и собственниками.
- [ ] Финансовые расчёты между участниками (комиссии агентов, оплата аренды) происходят вне платформы.
- [ ] Платформа предоставляет только технический инструмент для управления ТС (в т.ч. флотом), бронированием и данными.

### 8.2 Будущие модели монетизации (в перспективе)

#### 8.2.1 Возможные варианты развития
- [ ] **Процент от продаж:** В перспективе возможно введение комиссии с каждой брони (требует дополнительного обсуждения)
- [ ] **Дополнительные услуги:** Премиум-функции, расширенная аналитика, приоритетная поддержка
- [ ] **Интеграции:** Платные интеграции с внешними системами (CRM, платежные системы)
- [ ] **Реклама:** Размещение рекламы на платформе (опционально)

#### 8.2.2 Требования к архитектуре
- [ ] Система должна быть готова к добавлению различных моделей монетизации
- [ ] Гибкая система тарифов и подписок
- [ ] Интеграция с платежными системами для приёма оплаты за использование платформы
- [ ] Система учёта использования и биллинга

### 8.3 Реферальная программа как инструмент монетизации

- [ ] Реферальная программа для клиентов (см. раздел 7.3) способствует привлечению новых пользователей
- [ ] Косвенная монетизация через увеличение количества активных пользователей платформы
- [ ] Увеличение ценности платформы за счёт роста пользовательской базы

### 8.4 Учёт и отчётность по монетизации

- [ ] Система учёта подписок и платежей за пользование платформой
- [ ] Отчёты для собственников и агентов о стоимости использования
- [ ] История платежей и подписок
- [ ] Уведомления об истечении подписки или необходимости оплаты

## 9. Бизнес-требования: Функционал для агентов

### 9.1 Доступ к информации о транспортных средствах

#### 9.1.1 Просмотр доступных ТС
- [ ] Агент видит список всех ТС, к которым у него есть доступ через контракты
- [ ] Для каждого ТС доступна полная информация:
  - Описание и характеристики (согласно карточке типа ТС)
  - Фотографии и медиа-контент
  - Актуальные цены и правила ценообразования
  - Календарь доступности в реальном времени
  - Статус ТС (активно/неактивно)
- [ ] Фильтрация и поиск ТС по различным критериям (тип, локация, цена, доступность)

#### 9.1.2 Интеграция данных через API и виджеты
- [ ] **REST API:** Получение данных о ТС, доступности, ценах для интеграции на собственные площадки
- [ ] **Виджеты:** Готовые JavaScript-компоненты для встраивания на сайт агента
- [ ] **Синхронизация в реальном времени:** Автоматическое обновление данных о доступности и ценах
- [ ] **Выборка ТС в виджете:** агент может настроить, какие ТС отображаются в виджете: по умолчанию — все ТС по контрактам; опционально — выборка по критериям (тип ТС, локация, собственник, произвольный список выбранных ТС и т.п.), чтобы на разных площадках или страницах показывать разный набор
- [ ] **Кастомизация внешнего вида:** настройка виджетов под стиль и брендинг агентской площадки: темы, цвета, шрифты, логотип, при необходимости язык интерфейса виджета и размер/режим отображения (объём — по решению стейкхолдеров)

Детали интерфейса и интеграций для агентов см. разделы 12.3 и 12.4.

### 9.2 Управление бронями

#### 9.2.1 Создание и управление бронями
- [ ] Создание брони от имени клиента через интерфейс платформы или API
- [ ] Просмотр всех броней, созданных агентом
- [ ] Управление статусами броней (подтверждение, отмена, изменение)
- [ ] Добавление примечаний и дополнительной информации к броням

#### 9.2.2 Отслеживание и аналитика
- [ ] Статистика по броням (активные, завершённые, отменённые)
- [ ] Фильтрация броней по ТС, собственникам, клиентам, периодам
- [ ] История всех операций с бронями
- [ ] Информация о комиссиях (в перспективе)

### 9.3 Управление контрактами

#### 9.3.1 Просмотр контрактов
- [ ] Список всех активных контрактов с собственниками
- [ ] Информация о каждом контракте:
  - Список ТС, доступных по контракту
  - Период действия контракта
  - Условия и комиссии
  - Статус контракта
- [ ] История завершённых и истёкших контрактов

### 9.4 Комбинированная роль: Собственник-Агент

#### 9.4.1 Концепция совмещения ролей
- [ ] Один пользователь может быть одновременно собственником и агентом
- [ ] Собственник может выступать агентом для своих собственных ТС
- [ ] Единый интерфейс для управления обеими ролями

#### 9.4.2 Функционал комбинированного интерфейса
- [ ] **Разделение представления ТС:**
  - Собственные ТС (полный доступ: редактирование, управление доступностью, ценообразование)
  - ТС, доступные через контракты с другими собственниками (только просмотр и бронирование)
- [ ] **Единая панель управления:**
  - Объединённый календарь всех ТС (собственных и доступных через контракты)
  - Единый список всех броней (как собственника, так и агента)
  - Переключение между режимами просмотра (как собственник / как агент / все вместе)
- [ ] **Управление доступом:**
  - Собственник видит свои ТС с полным функционалом управления
  - Собственник видит те же ТС в режиме агента (как они видны другим агентам)
  - Возможность сравнения представления данных в разных ролях

## 10. Бизнес-требования: Заключение контрактов

Под контрактом в платформе понимается предоставление доступа к системе бронирования ТС (см. глоссарий).

### 10.0 Поиск и матчинг (связывание агента и собственника)

Связь «агент — собственник» может устанавливаться двумя способами:
- **Собственник ищет агента:** каталог/витрина агентов (или заявки от агентов), выбор и приглашение — текущий сценарий (см. 10.1.1).
- **Агент ищет собственника:** каталог собственников и/или ТС с возможностью отправить запрос на доступ; собственник принимает или отклоняет («матч» = предоставление доступа в платформе).

Тут подойдёт общий каталог, в котором можно искать по виду ТС (катер, вертолёт, трансфер и т.п.) и по ролям (агент, владелец). На первом этапе это базовый продукт; в версии 2.0 каталог и платформа расширяются за счёт добавления новой роли «Исполнитель» (гиды, танцоры, певцы, кавер-группы, диджеи и другие смежные исполнители), которые также становятся доступны для поиска и матчинга.

Требования к discovery и матчингу (объём — по решению стейкхолдеров, см. раздел 13):
- [ ] **Каталог для собственника:** поиск и просмотр агентов (регион, специализация) с возможностью пригласить к выбранным ТС
- [ ] **Каталог для агента:** поиск и просмотр собственников и/или предложений ТС с возможностью отправить запрос на доступ к выбранным ТС
- [ ] **Заявки на доступ:** агент отправляет запрос → собственник видит заявку и принимает/отклоняет → при принятии создаётся контракт (доступ в платформе)
- [ ] **Уведомления:** сторона, получившая запрос или приглашение, получает уведомление (email, в перспективе push)
- [ ] **Каталог без рейтингов на старте:** базовый каталог по ролям с карточками компаний; рейтинги и репутация не входят в MVP (см. версию 3.0 в разделе 12.1).

### 10.1 Процесс заключения контракта

#### 10.1.1 Инициация контракта собственником
- [ ] Собственник выбирает ТС из своего парка
- [ ] Собственник добавляет агента к выбранным ТС (внесение ID компании и прав доступа в карточку ТС, по аналогии с расшариванием в Google Calendar)
- [ ] Указание условий доступа:
  - Период действия контракта (дата начала и окончания)
  - Список ТС, доступных агенту
  - Условия комиссии (опционально, для внутреннего учёта)
- [ ] Агент получает уведомление о предоставлении доступа

#### 10.1.2 Инициация контракта агентом (запрос доступа)

- [ ] Агент находит собственника или ТС в каталоге платформы (поиск/фильтры: регион, тип ТС, условия)
- [ ] Агент отправляет запрос на доступ к выбранным ТС (с возможностью указать период и комментарий)
- [ ] Собственник видит входящие заявки и может принять или отклонить
- [ ] При принятии платформа создаёт контракт (доступ); агент получает уведомление и доступ к API/виджетам
- [ ] При отклонении агент получает уведомление (опционально: с причиной или без)

#### 10.1.3 Управление контрактами
- [ ] Собственник может:
  - Добавлять новых агентов к ТС
  - Удалять агентов из доступа к ТС
  - Изменять список ТС, доступных агенту
  - Изменять период действия контракта
  - Приостанавливать или возобновлять доступ
- [ ] Агент видит список всех контрактов и доступных ему ТС

### 10.2 Важные ограничения

#### 10.2.1 Что НЕ входит в функционал платформы
- [ ] **Бумажные документы:** Платформа не хранит и не обрабатывает бумажные контракты
- [ ] **Электронный документооборот (ЭДО):** Платформа не предоставляет функционал для подписания электронных документов (в MVP)
- [ ] **Юридические аспекты:** Платформа не является участником юридических отношений между собственником и агентом
- [ ] **Ответственность за споры:** Платформа не отвечает за разрешение споров между сторонами; споры регулируются непосредственно участниками вне платформы
- [ ] **Платежи между сторонами:** Платформа не обрабатывает финансовые расчёты между собственником и агентом (в MVP)

#### 10.2.2 Что предоставляет платформа
- [ ] Технический доступ агента к информации о ТС
- [ ] **Управление правами доступа в карточке ТС:** в карточке каждого ТС должна быть графа/настройка для добавления ID компании и прав доступа — по аналогии с «расшариванием» в Google Calendar, но на основе ID компании в системе (не email)
- [ ] Управление правами доступа (кто может видеть какие ТС)
- [ ] Отслеживание активности (кто создал бронь, когда)
- [ ] Инструменты для интеграции данных на площадки агентов
- [ ] **Хранение документов:** в версии 2.0 при появлении полноценной CRM планируется хранение подписанных контрактов и связанных документов

### 10.3 Связь контрактов с функционалом

- [ ] При создании контракта автоматически предоставляется доступ к API и виджетам
- [ ] Агент получает API-ключи для доступа к данным по контракту
- [ ] При изменении или отмене контракта доступ автоматически обновляется или блокируется
- [ ] История изменений контрактов сохраняется для аудита

## 11. Основной рабочий процесс (Workflow)

### 11.1 Полный цикл аренды

```
1. РЕГИСТРАЦИЯ И УСТАНОВКА
   Собственник регистрируется → Указывает данные о ТС → Устанавливает цены → Условия бронирования

2. ДОСТУПНОСТЬ И КАЛЕНДАРЬ
   Собственник указывает периоды доступности (разовые и повторяющиеся)
   → В календаре помечены даты: доступно, забронировано, недоступно

3. ЗАКЛЮЧЕНИЕ КОНТРАКТА
   Вариант А: Собственник добавляет агента к выбранным ТС через интерфейс платформы
   Вариант Б: Агент находит собственника/ТС в каталоге → отправляет запрос на доступ → собственник принимает или отклоняет
   → Платформа создает техническую связь между агентом и ТС собственника
   → Агент получает доступ к информации о ТС и интеграционным инструментам (виджет/API)
   → **Примечание:** Юридические документы, ЭДО и бумажные контракты оформляются вне платформы

4. ПУБЛИКАЦИЯ НА ПЛОЩАДКЕ АГЕНТА
   Агент размещает информацию о ТС на своей платформе
   → Использует виджет или интегрирует через API
   → Клиент видит актуальную информацию (цены, доступность)

5. БРОНИРОВАНИЕ
   Клиент выбирает ТС и дату на площадке агента
   → Система регистрирует бронь в календаре собственника
   → Информация о авансе (если требуется) попадает в платформу

6. КООРДИНАЦИЯ
   Агент связывается с клиентом и собственником (офлайн, через мессенджеры)
   → Организует успешную передачу ТС
   → Платформа отслеживает статус брони

7. ЗАВЕРШЕНИЕ
   Аренда завершена → Статус обновляется в системе
   → Возможны отчеты по выручке и коммиссиям
```

### 11.2 Стратегия платформ

**Первая итерация (MVP):**
- Разработка веб-платформы как основного решения
- Обеспечение полной функциональности через браузер на всех устройствах
- Адаптивный дизайн для мобильных устройств

Целевое состояние по платформам и продукту см. раздел 1.2, п. 1.2.3.

## 12. Функциональные требования

Раздел 12 описывает реализацию требований из разделов 4–11: интерфейсы пользователей (собственник, агент), API и виджеты, управление бронями и уведомлениями.

### 12.1 Концепция интерфейса

- [ ] **Единый интерфейс вместо двух раздельных**  
  - Не создаются два полностью разных интерфейса для ролей собственника и агента.  
  - Один и тот же пользователь может одновременно выступать в роли собственника и агента, поэтому интерфейс должен поддерживать совмещение ролей без переключения между разными продуктами.

- [ ] **Основная навигация по задачам, а не по ролям**  
  - Верхний уровень интерфейса организован вокруг ключевых сценариев: управление флотом и управление продажами.  
  - Стейкхолдерский вариант (Витя): вкладки в духе CRM — **«Собственный флот» | «Продажи»**.  
  - При необходимости вкладки могут расширяться (например, «Аналитика», «Настройки»), но базовая логика остаётся: пользователь заходит в задачу, а не в «роль».

  **Версия 1.0: базовый операционный контур**
  - **Календарь.**  
    - Инструмент работы собственника и агента с текущими бронями.  
    - Ручное занесение новых броней.  
    - Поиск по календарям добавленных ТС.  
    - Система поиска свободного ТС (основа проекта 1).
  - **Флот / Парк.**  
    - Инструмент для добавления ТС с технической точки зрения.  
    - Управление виджетами и клиентской информацией по ТС.  
    - Быстрый переход в нужный календарь по каждому ТС.  
    - Отображение информации о собственнике и его контактах.  
    - Разделение на собственный флот и агентский флот (ТС, в которые пользователя добавили как агента) с разницей в доступном функционале и опциях.
  - **Каталог партнёров (собственники и агенты).**  
    - Единый список партнёров, где можно найти контрагента и отправить запрос на заключение контракта.
  - **Базовая аналитика по календарю.**  
    - Для собственника: сколько часов отработала каждая лодка, от каких агентов пришли брони.  
    - Для агента: сколько часов загрузки он обеспечил каждой лодке/собственнику.
  - **Доступы и настройки компании.**  
    - Выдача логинов/паролей для сотрудников, управление их правами и ролями.  
    - Настройки уведомлений и другого базового функционала.  
    - Управление тарифом и оплатой.  
    - Каналы техподдержки и коммуникации с командой продукта.
  - **База знаний.**  
    - Обучающие материалы и инструкции по работе с платформой.

  **Версия 2.0: CRM и расширенная работа с клиентами**
  - **CRM-менеджмент.**  
    - Система для работы менеджеров внутри компании.  
    - Коммуникация с клиентами и ведение сделок непосредственно из платформы.
  - **База клиентов.**  
    - Сбор и хранение контактных данных.  
    - Быстрый поиск по клиентам и компаниям.  
    - Переход в связанные сделки и брони.
  - **Реферальная программа.**  
    - Инструменты лояльности и реферального маркетинга (промокоды, реферальные ссылки и т.п.).
  - **Расширенная аналитика.**  
    - Отчёты по клиентам, движению денег, эффективности работы менеджеров и другим ключевым показателям.
  - **Инструменты продуктивности.**  
    - Задачи, проекты, доски и другие элементы для управления операционной работой.
  - **Store интеграций.**  
    - Подключение входящих/исходящих интеграций: телефония, метрики по Telegram/WhatsApp, виджет чата на сайт, формы заявок и т.д.

  **Версия 3.0: сообщество и оценка качества**
  - **Форум и комьюнити-инструменты.**  
    - Пространство для обмена опытом между собственниками, агентами и исполнителями.
  - **Система рейтингов и оценок.**  
    - Инструменты оценок, отзывов и форматов «круглого стола» — только после формирования зрелой экосистемы, с учётом рисков монополизации и ответственности платформы за честность рейтингов.

- [ ] **Меню и визуализация по ролям**  
  - Меню для собственников и агентов различается (добавление техники, управление доступами — с учётом роли).  
  - У собственников и агентов разные параметры и отчёты — это влияет на визуализацию данных и формирование отчётов.  
  - Концепт интерфейса единый для всех ролей; детальная визуализация и отображение вкладок передаются на проработку дизайнеру.

- [ ] **Кейсы интерфейса (вижн Вити)**  
  - Рассматриваются два ключевых среза:  
    - **Функционал собственника** (управление флотом, доступностью, ценами, контрактами, пилотами).  
    - **Функционал агента** (продажи, витрина, воронка, работа с клиентами).  
  - Флот внутри интерфейса должен явно разделяться на:  
    - «Свой» флот (юридически принадлежащие ТС).  
    - ТС, добавленные **в управление** по договорам (ведутся как управляемый флот).  
  - **_`#to_review:`_**
  - [ ] **Action Item (Витя):** сформировать и продемонстрировать целевой вижн интерфейса по разделению флота на «свой» и «в управлении» в рамках вкладок «Собственный флот» | «Продажи».

- [ ] **Вкладка «Собственный флот»**  
  - Отображает все ТС, по которым пользователь выступает собственником или управленцем с полными правами:  
    - ТС, которыми он владеет (100% прав пользования и распоряжения).  
    - ТС, взятые в управление по договору и ведущиеся как собственный парк (управление операционкой, но без права отчуждения).  
  - Для каждого такого ТС доступны «глубокие» данные:  
    - Полный набор характеристик и технических параметров.  
    - Полная финансовая информация (цены, скидки, себестоимость — если предусмотрено стейкхолдерами).  
    - Вся история броней, статусов, комментариев.  
    - Управление доступностью, ценообразованием, контрактами с агентами и пилотами.

- [ ] **Вкладка «Продажи»**  
  - Фокус на задачах агента:  
    - Все ТС, которые пользователь продаёт как агент (в т.ч. собственный флот и ТС по агентским/управленческим договорам).  
    - Витрина ТС «глазами рынка»: описание, фото, доступность, конечные цены.  
    - Воронка продаж: лиды, заявки, брони, статус исполнения.  
  - Для каждого ТС в этом контексте пользователь видит только те данные, которые доступны по его роли:  
    - Как агент: ограниченный набор полей (без «внутренней кухни» собственника).  
    - Как собственник: полный объём данных, даже если ТС также продаётся через других агентов.

- [ ] **Правила видимости данных по ролям**  
  - Собственник видит **больше информации**, чем агент, по одному и тому же ТС:  
    - Внутренние финпоказатели (себестоимость, маржа, реальные расходы) доступны только собственнику.  
    - Агент видит клиентскую цену, агентскую комиссию (если предусмотрено) и данные, необходимые для продаж.  
  - Один и тот же объект ТС может отображаться в интерфейсе с разной глубиной в зависимости от прав пользователя.

- [ ] **Гибкая модель «владения» и «управления» ТС**  
  - Пользователь как агент может:  
    - Поставить собственное судно в управление (добавить его в «Собственный флот» и одновременно в витрину «Продажи»).  
    - Взять судно в управление по договору и продавать его как часть своего управляемого флота.  
  - Интерфейс должен различать:  
    - ТС, которыми пользователь владеет.  
    - ТС, которые он ведёт в управлении (управленец, но не юридический собственник).  
    - ТС, к которым у него есть только агентский доступ (только продажи, без операционного управления).

- [ ] **Единые сущности — разные представления**  
  - Базовые сущности (ТС, брони, контракты, клиенты) одни и те же для всех ролей.  
  - Разные роли и вкладки управляют **представлением** и уровнем детализации, а не дублируют данные.

- [ ] **Дальнейшая детализация интерфейса**  
  - Текущие чек-листы по `Интерфейсу собственника` и `Интерфейсу агента` (подразделы 12.2+ ниже) описывают функциональные блоки внутри этой общей концепции.  
  - При проектировании UI/UX необходимо опираться на вышеописанную модель вкладок и видимости данных.

### 12.2 Интерфейс собственника (Owner Portal)

#### 12.2.1 Управление ТС
- [ ] Создание профиля ТС с полной информацией:
  - Название, тип, марка, модель
  - Описание, фотографии (галерея)
  - Технические характеристики (вместимость, скорость, т.д.)
  - **Требования к пилоту/оператору:**
    - Наличие пилота (обязательно / не требуется)

### 12.4 API и интеграции для агентов

#### 12.4.1 REST API (для площадок агентов)

**Основные endpoints:**

- **GET /api/v1/properties** - Список всех ТС, доступных агенту
  - Параметры: фильтры, пагинация, поля
  - Возвращает: ID, описание, фото, базовую цену

- **GET /api/v1/properties/{id}** - Детали одного ТС
  - Возвращает: полное описание, характеристики, требования

- **GET /api/v1/properties/{id}/availability** - Календарь доступности ТС
  - Параметры: дата начала, дата конца
  - Возвращает: статус каждого дня (доступно, забронировано, недоступно), цена

- **GET /api/v1/properties/{id}/pricing** - Информация о ценах
  - Возвращает: базовая цена, периодические цены, скидки

- **POST /api/v1/bookings** - Создание новой брони
  - Параметры: ТС, дата начала, дата конца, данные клиента
  - Возвращает: ID брони, статус, детали

- **GET /api/v1/bookings/{id}** - Детали брони
  - Возвращает: полная информация о брони и её статусе

- **PATCH /api/v1/bookings/{id}** - Обновление статуса брони
  - Параметры: новый статус, примечания
  - Возвращает: обновленную бронь

#### 12.4.2 Виджет для встраивания
- JavaScript-компонент для встраивания на сайт агента
- Функциональность:
  - Поиск ТС по типу, локации
  - Фильтр по датам и ценовому диапазону
  - Отображение доступности в интерактивном календаре
  - Оформление брони (редирект на страницу платежа/подтверждения)
- **Выборка ТС:** возможность настройки набора ТС, отображаемых в виджете — все ТС по контракту или выборка по критериям (тип, локация, собственник, выбранный список); на разных площадках/страницах агент может показывать разный набор (см. §9.1.2)
- **Кастомизация:** темы, цвета, логотипы; при необходимости шрифты, язык интерфейса виджета, размер/режим отображения (см. §9.1.2)

#### 12.4.3 Webhooks (в перспективе)
- Уведомления платформы агенту об изменениях:
  - Новая бронь
  - Отмена брони
  - Изменение доступности ТС
  - Обновление цены

#### 12.4.4 Синхронизация календарей
- [ ] **Цель:** дублирование информации и поддержка привычных инструментов пользователей в разных странах (Google Calendar, Outlook и др.)

### 12.5 Система управления бронями и платежами

#### 12.5.1 Жизненный цикл брони
```
Создана → Подтверждена → В процессе → Завершена
            ↓
         Отменена (может быть на любом этапе)
```

#### 12.5.2 Статусы брони
- **Создана (Created)** - Клиент заполнил форму
- **Подтверждена (Confirmed)** - Агент подтвердил бронь
- **В процессе (In Progress)** - Аренда активна
- **Завершена (Completed)** - Аренда закончилась
- **Отменена (Cancelled)** - Клиент или агент отменили

#### 12.5.3 Управление авансами
- [ ] Отслеживание авансовых платежей (если требуются)
- [ ] Сохранение информации о сумме, сроке, статусе (оплачено/не оплачено)
- [ ] История платежей для каждой брони
- [ ] **В MVP:** Платформа регистрирует информацию о платежах, но не обрабатывает их (платежи - ответственность агента и собственника)

#### 12.5.4 Календарь блокировок
- [ ] Автоматическое блокирование даты ТС при создании брони
- [ ] Система не позволяет создать две брони на одни и те же даты
- [ ] История изменений статуса блокировки

#### 12.5.5 Базовая аналитика (версия 1.0)
Минимальный набор метрик для операционной работы:
- [ ] **Информация по прогулке:** данные, вносимые в календарь (даты, ТС, участники, статус)
- [ ] **Входящие/исходящие денежные потоки:** движение денег и распределение по участникам (агент, собственник, платформа)
- [ ] **Общие часы по лодке/ТС:** наработка часов по каждому ТС за период
- [ ] **Учёт часов и з/п капитана:** часы работы капитана и расчёт заработной платы

### 14.3 Архитектура масштабируемости

#### 14.3.1 Горизонтальное масштабирование

**Backend масштабирование:**
- [ ] **Stateless архитектура:** Все серверы приложений должны быть stateless (без сохранения состояния сессии на сервере)
- [ ] **Load Balancing:** Использование балансировщиков нагрузки для распределения запросов между несколькими инстансами
- [ ] **Микросервисная архитектура (в перспективе):** Возможность разделения на независимые сервисы для независимого масштабирования
- [ ] **Автоматическое масштабирование:** Автоматическое добавление/удаление инстансов в зависимости от нагрузки

**База данных масштабирование:**
- [ ] **Репликация:** Master-slave репликация для чтения (read replicas)
- [ ] **Шардирование:** Горизонтальное разделение данных по шардам при необходимости
- [ ] **Кэширование:** Многоуровневое кэширование (Redis, CDN) для снижения нагрузки на БД
- [ ] **Индексация:** Оптимизация индексов для быстрого поиска и фильтрации

**Frontend масштабирование:**
- [ ] **CDN:** Использование CDN для статических ресурсов (изображения, JS, CSS)
- [ ] **Кэширование на клиенте:** Service Workers для кэширования и офлайн-работы
- [ ] **Lazy loading:** Ленивая загрузка компонентов и данных

#### 14.3.2 Вертикальное масштабирование

- [ ] Возможность увеличения ресурсов (CPU, RAM, диск) на существующих серверах
- [ ] Оптимизация использования ресурсов через профилирование и мониторинг
- [ ] Выбор подходящих инстансов для разных типов нагрузки

#### 14.3.3 Масштабирование по пользователям

## 16. Риски и ограничения

### 16.1 Риски
- **Юридическая сложность:** Разные страны - разное законодательство (лицензирование, ответственность)
- **Конкуренция:** Существуют локальные решения в разных странах
- **Привлечение пользователей:** Холодный старт - нужны пилотные клиенты
- **Интеграция платежей:** Разные системы в разных странах - сложность

### 16.2 Ограничения MVP
- Все уведомления только по email
- Платежи не обрабатываются платформой
- Нет встроенного мессенджинга
- Однострочные контракты (минимум полей)
- Языки MVP: русский и английский

## Приложение A: Примеры использования (Use Cases)

### UC1: Собственник добавляет новое ТС
```
1. Собственник авторизуется
2. Нажимает "Добавить ТС"
3. Заполняет форму (название, тип, фото, цена)
4. Указывает, нужен ли пилот
5. Сохраняет ТС
6. В календаре появляется новая запись
7. По умолчанию ТС помечено как "недоступно"
8. Собственник добавляет периоды доступности
```

### UC2: Агент заключает контракт с собственником
```
1. Агент авторизуется
2. Нажимает "Заключить контракт"
3. Выбирает собственника из списка (или добавляет нового)
4. Выбирает ТС собственника
5. Указывает % комиссии
6. Сохраняет контракт
7. Получает API-ключ и документацию
8. Становится видна информация о ТС и график доступности
```

### UC3: Клиент бронирует ТС через виджет агента
```
1. На сайте агента клиент видит виджет с ТС
2. Выбирает ТС и даты в календаре
3. Видит цену
4. Нажимает "Забронировать"
5. Заполняет форму (имя, контакты)
6. Подтверждает бронь
7. Агент и собственник получают уведомление
8. Дата помечена как "забронирована"
9. В календаре собственника видна бронь с деталями клиента
```

### UC4: Отработка конфликта (двойное бронирование)
```
1. Собственник забронировал ТС на себя (личное использование)
2. Клиент пытается забронировать на эту же дату через виджет
3. Система показывает ошибку "Дата недоступна"
4. Клиент выбирает другую дату
5. Бронь создается успешно
```

## Приложение B: Глоссарий

| Термин | Описание |
|--------|----------|
| **ТС** | Транспортное средство (лодка, автомобиль, вертолёт и т.д.) |
| **Собственник** | Владелец ТС, публикует информацию и управляет доступностью |
| **Агент** | Промежуточный участник, получает доступ по контрактам с собственниками и размещает на своих площадках |
| **Клиент** | Конечный пользователь, арендует ТС через площадку агента |
| **Бронь** | Зарезервированное ТС на определённые даты с указанием клиента |
| **Контракт** | В платформе: предоставленный посредством платформы доступ к системе бронирования ТС собственника (список ТС, календарь, брони). Юридические договоры между агентом и собственником оформляются вне платформы. |
| **Контрол** | Элемент управления в интерфейсе (кнопка, поле ввода, переключатель и т.п.); от объёма доступных контролов зависит разделение ролей. |
| **Авансовый платеж** | Частичная предоплата перед арендой |
| **Комиссия** | Процент от стоимости аренды, который платит агент платформе или собственнику платит агенту |
| **API-ключ** | Уникальный идентификатор для аутентификации API запросов агента |
| **Виджет** | JavaScript компонент для встраивания на сайт агента |
| **PWA** | Progressive Web App - веб-приложение, работающее как нативное приложение |
| **Escrow** | Депозит, удерживаемый третьей стороной до выполнения условий |
